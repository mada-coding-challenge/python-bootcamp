
# Guided Lab: Evolve the Product Schema in Django

This project demonstrates how to safely evolve a database schema in Django without data loss, downtime, or database constraint violations. It covers adding a non-nullable, unique field (`code`) to existing records using a data migration, inspecting migration plans, and performing a rollback test.

---

## Lab Objectives

1. Add a nullable field to a pre-populated model.
2. Generate named schema migrations and inspect them (`showmigrations`, `migrate --plan`, `sqlmigrate`).
3. Build a custom data migration (`RunPython`) to populate field values for existing records.
4. Enforce schema constraints (`null=False`, `unique=True`).
5. Perform a migration rollback and verify data integrity.

---

## Schema Evolution Steps

### Step 1: Add `code` as Nullable

Add `code` to `products/models.py` with `null=True` so database records can accept empty values temporarily:

```python
from django.db import models

class Product(models.Model):
    name = models.CharField(max_length=100)
    price = models.DecimalField(max_digits=10, decimal_places=2)
    stock = models.IntegerField()
    code = models.CharField(max_length=50, null=True, blank=True)

```

---

### Step 2: Create Named Schema Migration

Generate a migration file named `add_product_code_nullable`:

```bash
python manage.py makemigrations products --name add_product_code_nullable

```

---

### Step 3: Inspect Pending Migration & Apply

Inspect the execution plan and SQL queries prior to running the migration:

```bash
# View migration status across apps
python manage.py showmigrations products

# View execution plan
python manage.py migrate --plan

# View underlying SQL generated by Django
python manage.py sqlmigrate products 0002_add_product_code_nullable

# Apply migration to database
python manage.py migrate

```

---

### Step 4: Create Empty Data Migration

Generate an empty migration file for the custom data population logic:

```bash
python manage.py makemigrations products --empty --name populate_product_code

```

---

### Step 5: Populate `code` Data via `RunPython`

Edit `products/migrations/0003_populate_product_code.py` to auto-generate unique codes for existing product records based on their primary key (`id`):

```python
from django.db import migrations

def populate_code(apps, schema_editor):
    Product = apps.get_model('products', 'Product')
    for product in Product.objects.all():
        product.code = f"PROD-{product.id}"
        product.save()

def reverse_populate_code(apps, schema_editor):
    Product = apps.get_model('products', 'Product')
    Product.objects.all().update(code=None)

class Migration(migrations.Migration):

    dependencies = [
        ('products', '0002_add_product_code_nullable'),
    ]

    operations = [
        migrations.RunPython(populate_code, reverse_populate_code),
    ]

```

Run the data migration:

```bash
python manage.py migrate

```

---

### Step 6: Enforce `null=False` and `unique=True` Constraints

Now that all existing rows contain a valid `code`, update `products/models.py` to enforce required constraints:

```python
class Product(models.Model):
    name = models.CharField(max_length=100)
    price = models.DecimalField(max_digits=10, decimal_places=2)
    stock = models.IntegerField()
    code = models.CharField(max_length=50, null=False, unique=True)

```

Generate and apply the migration:

```bash
python manage.py makemigrations products --name enforce_code_not_null_unique
python manage.py migrate

```

### Step 8: Apply, Verify Data & Test Rollback

#### Data Verification

Open the Django shell:

Verify that existing product rows have `code` populated:

#### Migration Rollback Test

Test reversing database changes safely:

```bash

```

Verify in shell that `code` is revertible (`None`):

```python

```

Re-apply all migrations to restore database to latest state:

```bash
python manage.py migrate

```

## Exit Ticket Answer

> **Question:** Explain why `code` becomes required (`null=False`) only after the data migration.

**Answer:**

If a column is defined as `null=False` at the moment it is added, the relational database engine requires every pre-existing row to immediately have a valid value for that column. Since existing rows do not have values for the new field yet, the database engine will reject the migration with an integrity error.

By using a safe 3-phase migration sequence:

1. **Schema Change 1:** Add `code` as nullable (`null=True`). Existing rows receive `NULL`.
2. **Data Migration:** Populate every existing row with a valid unique value (`PROD-1`, `PROD-2`, etc.) via Python script.
3. **Schema Change 2:** Alter `code` to `null=False` and `unique=True`.

Because no row contains `NULL` values when Phase 3 runs, the database can safely apply the NOT NULL constraint without error or downtime.
